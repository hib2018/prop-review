# prop-review

[English README](README.md)

提案を項目ごとにレビューするローカルCLIです。ソースコードは `src/` にあります。

## インストール

このリポジトリのルートで実行し、`~/.local/bin` を `PATH` に追加してください。対話コマンドには、`/dev/tty`、`PATH` 上の `stty`、ANSI互換端末を備えたUnix系環境が必要です。標準入力のパイプや非対話型エージェントのシェルは制御端末の代わりにはならず、ネイティブWindows端末には対応していません。

```sh
mkdir -p "$HOME/.local/bin"
go build -o "$HOME/.local/bin/prop-review" ./src
# 短縮コマンド（既存の prev は上書きしない）
if ! command -v prev >/dev/null 2>&1 && [ ! -e "$HOME/.local/bin/prev" ] && [ ! -L "$HOME/.local/bin/prev" ]; then
  ln -s prop-review "$HOME/.local/bin/prev"
fi
```

非対話型エンジン要求の対応OSはmacOSとLinuxです。各コマンド（`npm root -g` を含む）を専用プロセスグループで起動し、タイムアウトまたは標準出力・標準エラーの上限超過時は、子孫を含むグループ全体に直ちにSIGKILLを送信します。`setsid` などで意図的にグループから離脱した子孫は保証対象外です。他OSではプロセス起動前にエラーを返します。対話型の `ingest` セッションにはこの停止方針を適用しません。

インストールではバイナリと短縮コマンドのリンクだけを配置し、ホームディレクトリにスキルは配置しません。CLIや同梱スキルのソースを更新した場合は、上記の `go build` を再実行してください。

### 利用するリポジトリの初期化

対象のGitリポジトリ内で実行します。

```sh
prev init
```

両スキルをリポジトリ内の `.pi/skills/` と `.agents/skills/` に配置し、作業用の `prop-review-tmp/` を作成します。ホーム側へのスキル配置は不要です。既存のホーム側スキルは後方互換の探索先として引き続き利用できますが、この手順では変更・削除しません。競合時の動作や起動済みエージェントの再読み込み手順は、後述の `init` を参照してください。

## コマンド

Gitリポジトリ内で実行します。画面上ではリポジトリ内のパスを短く表示し、`prop-review-tmp/` 以下は共通部分を省いて `review.xxx/proposal.txt` のように表示します。実際のファイルは `prop-review-tmp/` 以下にあり、コマンドへパスを直接渡す際にはその接頭辞が必要です。`prev` は `prop-review` と同じコマンド・引数を受け付ける短縮名です（例: `prev flow`）。`generate`、`issue`、`revise`、`clarify`、`ingest`、`diff`、`flow` はリポジトリの `prop-review-tmp/` を使用します。`diff` は承認済み項目と現在の作業ツリーを比較し、`flow` は検証済みレビュー履歴の承認済み項目を実行します。

### `prop-review init` / `prev init`

```sh
prop-review init
# 同じ動作の短縮コマンド:
prev init
```

Gitリポジトリのルートでもサブディレクトリでも実行でき、常にリポジトリのルートを初期化します。Gitリポジトリ外で実行するとエラーになります。

- `prop-review-tmp/` を作成します。既存の提案・レビュー結果は保持し、提案生成やレビューは開始しません。必要な場合だけリポジトリのローカルGit `info/exclude` に `/prop-review-tmp/` を追加します。`.gitignore` やグローバルのGit除外設定は変更しません。
- リポジトリルートの `.pi/skills/` と `.agents/skills/` の両方に、`prop-review` と `prop-review-ingest` の両スキルを、それぞれの `SKILL.md` を含めてコピーします。これらのスキルディレクトリは自動ではGitの除外対象にならないため、追跡するかは自分で判断してください。
- CLIバイナリに埋め込まれたコピーを使い、ネットワークアクセスやダウンロードは行いません。同梱スキルを更新するにはバイナリを再ビルドしてください。
- 既存ファイルの内容が同一なら再実行しても変更しません。内容の異なるファイルやシンボリックリンクは競合として扱い、決して上書きしません。競合は自分で解消してから再実行してください。
- エージェントのグローバル設定、ホームディレクトリ内のスキル、ユーザー単位のエンジン設定は変更しません。

初期化後、起動済みエージェントのスキル検出を、そのエージェントが対応する方法で更新してください。Piでは `/reload` が使えます。他のエージェントでは対応する再読み込み方法を使うか、このリポジトリ内でエージェントを再起動してください。Piのコマンドがfxなどでも使えるとは限りません。

### `prop-review` / `prop-review proposal.txt [result.txt]`

未レビューの提案が1件なら開き、複数なら一覧から選択します。直接ファイルを指定することもできます。例:

```sh
prop-review
prop-review prop-review-tmp/review.123/proposal.txt
prop-review proposal.txt /path/to/result.txt
```

`a` + Enterで承認、`c` + Enterでコメント、Enterだけで未確認、`b` + Enterで戻り、`q` + Enterで保存せず終了します。全角ラテン文字キーにも対応します。コメントが空の場合は未確認になることを警告し、Enterで確定、Escで戻れます。依頼文・コメント入力は左右キー、Home/End、Backspaceに対応し、コメントの上限は1 MiBです。結果は通常、提案の隣の `proposal.review.txt` に保存し、パスを表示します。既存結果は上書きしません。別の結果パスを指定できますが、その結果は `revise` や `clarify` の履歴には使えません。

レビュー中に対象項目の説明が必要なら、承認・コメントを選ぶ画面で `e` + Enterを入力し、続けて質問を入力します。質問を空にしてEnterを押すと詳しい説明を求めます。設定済みのPi/fxがリポジトリと現在の提案一覧を参照し、回答をCLIに表示した後、同じ項目のレビューに戻ります。質問・回答は保存されず、承認・コメントにもなりません。各質問は独立しており、以前の質問・回答は引き継ぎません。エンジンが失敗してもレビューを続行できます。エンジンのインストール・認証が必要で、100秒でタイムアウトします。実装やファイル変更は指示しませんが、fxのツール権限は指示だけでは強制できません。

### `prop-review ingest [NAME]`

```sh
prop-review ingest          # 設定済みエンジンを起動（初期値はpi）
prop-review ingest fx       # 今回だけ変更。piまたはfxのみ指定可能
```

このGitリポジトリで対話型エージェントを起動し、`prop-review-ingest` に従って最新の完了済みレビュー（`proposal.txt` の更新時刻で選択）の履歴を検証し、結果の報告とコメントへの回答をチャットで行います。結果がなければエージェントが結果ファイルのパスを尋ねます。CLIとスキルはレビュー結果を変更せず、実装も開始しません。対象のCLIをインストール・認証してください。スキルは、まずこのリポジトリ内のエンジン別ディレクトリ（Piなら `.pi/skills/`、fxなら `.agents/skills/`）の `prop-review-ingest/SKILL.md` を優先し、次にもう一方のリポジトリ内ディレクトリを探します。その後に限り、従来のホーム側フォールバックとして `~/.agents/skills/prop-review-ingest/SKILL.md`、`~/.pi/agent/skills/prop-review-ingest/SKILL.md` の順に探します。`prop-review init` で両方のローカルコピーを配置できます。fxには選択したスキルのパスを明示して渡します。`fx` は対話起動時の初期プロンプト指定に対応しないため、`fx ask --json --prompt-permissions` で新しい初回応答を保存し、JSON応答の `session_id` を指定した `fx --resume <id>` でそのセッションだけを開きます。ID欠落・不正応答・初回処理失敗時は再開せず、最新セッションにもフォールバックしません。結果の要約とコメントへの回答は、選択した提案本文と同じ言語で行うよう指示します。各エージェントの設定・ツール権限が適用され、`ingest` 自体はサンドボックスを設定しません。

### `prop-review generate`

```sh
prop-review generate
```

依頼文を入力して提案を生成し、すぐレビューを開始します。依頼文は最大256 KiBのUTF-8で、前後の空白を除きます。元の依頼はルートの `request.txt` に保存されます。レビューを中断した場合も生成済みの未レビュー提案は残ります。

### `prop-review issue`

```sh
prop-review issue
```

認証済みの `gh` CLIが認識するGitHubリポジトリで、開いているissueを選んで提案を生成・レビューします。候補は `gh issue list` の既定の最初の30件です。タイトル・本文・番号・URLをエンジンへ渡し、その初回スナップショットをルート提案の `issue.json` に保存します。`request.txt` はタイトルのみで、Issue・ルート選択画面にも本文は表示しません。保存に失敗した場合は不完全な提案ディレクトリを削除し、レビューを開始しません。JSONで256 KiBを超えるissueは保存・読込ともに拒否し、空本文は受け付けます。破損JSONや非通常ファイルも読込エラーになります。issue自体は変更しません。

`revise`・`clarify` は検証済み履歴のルートにある `issue.json` を元の要件・制約の文脈として引き継ぎます。子世代には複製せず、GitHubから再取得しないため、後からIssueが編集されても初回の内容を使います。Issue本文自体は承認や実装許可ではなく、後続の承認・コメントと併せて解釈します。スナップショットのない手入力・既存系列は従来どおり依頼文とレビュー履歴だけを使い、Issueを推測して取得しません。

### `prop-review revise [proposal.txt]`

```sh
prop-review revise
prop-review revise prop-review-tmp/review.123/proposal.txt
prop-review  # 改訂後の提案を別途レビュー
```

コメント付きのレビュー済み提案を選ぶか、同じリポジトリ内の提案パスを指定します。改訂では、元の依頼と全コメントを含むレビュー履歴全体から提案を総合的に再構成します。承認済みの判断は制約として維持しますが、文言や構成は変更でき、未確認項目も変更できます。項目の統合・分割・追加・削除・並べ替えが可能で、位置による対応付けは行いません。生成される全項目は未承認（`Approval/Comment:` は空欄）です。以前の承認は履歴上有効なままですが、新しい項目には移されません。承認済みの判断との意味的な整合性は機械的には証明されず、人によるレビューが必要です。新しい `review.*` ディレクトリには `parent.txt` で履歴をつなぎ、内容が厳密に `restructure\n`（末尾改行あり）の `revision.txt` を保存します。**改訂後のレビューも実装も自動開始しません。** コメントがなく未確認だけの場合は改訂できません。隣接するレビュー結果がない場合や不一致の場合も失敗します。

### `prop-review clarify`

```sh
prop-review clarify
```

ルートの依頼文・issueタイトルから対象を選び、レビュー履歴全体を検証します。現在有効な未解決コメントがあれば、`revise` と共通の履歴・承認済み制約を使って提案全体を再構成します。未確認項目も含めて統合・分割・削除・追加・並べ替えができ、必要な追加確認も含めます。未解決項目が10件以上でもエンジンを呼び出し、生成結果に対して1～10件・形式・重複を検証します。新しい提案は `parent.txt` と `revision.txt`（`restructure\n`）で最新レビューにつなぎ、過去の承認を維持しつつ、それ以前の未解決項目を置き換えます。同じ文面も含めて新項目はすべて未承認です。有効なコメントがなければ未確認項目を維持して追加確認だけを探し、`followup.txt` と `parent.txt` を持つ提案に保存します。すべて解決済みで追加確認も不要なら保存しません。`clarify` は保存後にレビューだけを開始し、実装は開始しません。`revise` のレビュー非自動開始も維持します。ルートの `request.txt` も有効な `issue.json` もない旧レビュー、欠落・不正な結果や曖昧な履歴では失敗します。有効なルートの `issue.json` は `request.txt` より優先され、`request.txt` がなくてもタイトルから依頼を復元し、スナップショットから元のissue情報を取得します。`issue.json` が不正なら `request.txt` にフォールバックせず失敗します。生成失敗時は保存しません。

### `prop-review diff` / `prev diff`

```sh
prop-review diff
# 同じ動作の短縮コマンド:
prev diff
```

選択中のPi/fxを使い、明示的な承認済み項目と、未コミットの変更を含む現在のリポジトリルートの作業ツリーを意味的に比較します。Gitの行単位の差分ではありません。承認の収集は `flow` と同じ `flowApprovals` を使い、レビュー済みの全系列から過去の承認を含む明示的な承認済み項目を重複排除して集めます。未レビューの草案・未確認項目・コメント・元の依頼・Issue本文は対象外です。不正・曖昧な履歴では失敗し、承認がゼロならエンジンを起動しません。

未実装・部分実装の項目には、承認済み本文、不足内容、根拠となるファイル・位置（根拠がなければ明示的に「なし」）を表示します。判定不能の項目は理由付きで別に表示します。集計は `implemented`（実装済み）、`partial`（部分実装）、`missing`（未実装）、`unknown`（判定不能）の4状態すべてを対象にします。構造化応答は承認項目との対応・網羅性・状態値・必須報告項目などを検証し、重複フィールド・不正応答・エンジン失敗を「すべて実装済み」として扱いません。根拠パスはリポジトリ内の通常ファイルに解決できることを検査しますが、引用箇所がその挙動を証明しているかまでは機械的に保証しません。

実行用の `flowEngineResponse` ではなく参照用エンジンの `engineResponse` を再利用し、`diff` 専用のタイムアウトは10分です。PiはSDKのread/grep/find/lsツールだけを使います。fxは通常のローカル権限・設定を使用し、強制的な読み取り専用サンドボックスではありません。実装・ファイル変更・新規提案・承認や履歴の変更を指示で禁止し、新たな永続状態は作成しません。モックテストは実エンジンの権限制御や、ローカル設定・フック・プラグインによる副作用がないことを保証しません。

### `prop-review flow`

```sh
prop-review flow
```

現在のGitリポジトリの `prop-review-tmp/` にあるすべての完了済みレビュー履歴を読み込んで検証し（未レビューの草案は実行対象外）、承認済み項目をまとめて選択中のPi/fxに渡し、ツールを使って実行します。`flow` は図を生成するコマンドではなく、承認済み作業のためにリポジトリのファイルを参照・変更できます。未確認項目やコメントは文脈であり、実装の許可ではありません。

過去の承認は元の項目に対して保持されます。文言が同じでも、新しい項目や書き直した項目には承認を移しません。承認同士が競合する場合や、必要な依存作業の承認が欠けている場合は、それに依存する作業を停止します。推測で進めたり、競合する方針を暗黙に選んだり、未承認の前提作業を実装したりしません。不正・曖昧なレビュー履歴では実行を停止します。承認済み項目がゼロなら、エンジンを起動せず、何も変更しません。

CLIが渡すのは明示的な承認済み項目だけで、未確認項目・コメント・元の依頼は渡しません。意味上の矛盾・依存関係の検査や実装範囲の遵守はエンジンへの指示であり、サンドボックスによる保証ではありません。Piは参照・検索・編集・書込み・bashのツールを有効にし、権限フックを含む設定済みの拡張は保持します。探索したスキル・プロンプトテンプレート・コンテキストファイルは無効にします。fxは通常のローカル権限・設定を使用します。設定済みの拡張やフックには副作用があり得ます。実行タイムアウトは30分です。`prop-review flow --help`で短い使い方を表示します。

エンジンの失敗や権限制限は明示し、成功として扱いません。ツールの利用には選択したエンジンの権限が適用され、承認によって権限を回避することはありません。失敗前にファイルが変更されている可能性があるため、再実行前に作業ツリーを確認してください。自動ロールバックは前提にしません。提案・レビュー結果・過去の承認は保持し、新しい作業を許可するために書き換えません。

`PROP_REVIEW_FLOW_MODEL`（Piは `provider/model-id`、fxは対応するモデルID）と `PROP_REVIEW_FLOW_THINKING`（Piは `off`・`low`・`medium`・`high`、fxは `--effort` の対応値）でflowだけの設定を変えられます。未指定なら既定モデルを使用し、Piの推論量は `off`、fxは通常の設定です。これらは実行時のモデルと推論量の設定であり、図の生成やツール権限の設定ではありません。他コマンドの設定は変えません。

### `prop-review delete`

```sh
prop-review delete
```

未レビューの提案と、コメントがあり子の改訂がないレビュー済み提案から選びます。削除前に提案全文とレビュー結果（承認済み項目を含む）を表示し、`y/N` で確認し、`y`（または `Y`）で確定します。Enterやそれ以外は削除しません。`parent.txt` で参照されるディレクトリ、リンクや想定外のファイルがある候補は拒否します。確定すると選んだ `review.*` ディレクトリを**恒久的に削除**します。

### `prop-review doctor` / `prev doctor`

保存済みエンジン設定、必要コマンド、Pi選択時のSDK配置、Git除外の実効性（追跡済みファイルを含む）、危険なリンク・ファイル、履歴の欠落・分岐・循環・破損をローカルで読み取り専用診断します。末尾の未レビュー提案は正常として扱います。修復案の表示だけを行い、初期化・除外設定の変更・自動削除・履歴書換えはしません。エンジン起動・SDK import・認証確認や外部API呼出しも行いません。Piの配置確認にはログ出力と更新通知を無効にしたローカルの `npm root -g` を使用します。`gh` は `issue`、`pi` CLIはPiの `ingest` に必要です。終了コードは全チェック正常なら0、問題検出または診断失敗なら1です。修復案を確認し、変更は手動で判断してください。

### `prop-review engine` / `prop-review --engine NAME`

```sh
prop-review engine       # 現在のエンジンを表示
prop-review --engine pi  # piまたはfxのみ指定可能
prop-review --engine fx
```

対応エンジンは `pi` と `fx` だけです。エンジンはユーザー単位の設定（OSのユーザー設定ディレクトリ内の `prop-review/engine`）で、変更すると他のリポジトリでも使われます。設定がない場合の初期値は `pi` です。既存の保存済み設定が無効ならエラーとし、`prop-review --engine pi` または `prop-review --engine fx` で明示的に設定し直す必要があります。暗黙のフォールバックは行いません。使用するエンジンのインストールと認証が必要です。Piでの生成はNode.jsとグローバルnpmパッケージ `@earendil-works/pi-coding-agent` のSDKを使用し、`pi` CLIを直接呼びません。fxでの生成は `fx ask --no-save --json` を使い、JSON応答の `final_output` だけを読み取り、蓄積された出力は使いません。`ingest` は前述の方法で選択したエンジンの対話型CLIを起動します。

## ファイル形式と履歴

`proposal.txt` は項目ごとに「単一行の提案文」と空の `Approval/Comment:` 欄を持ちます。提案の言語は依頼に合わせます。例（組み込みコマンドではありません）:

```text
現在の設定をエクスポートするコマンドを追加する
Approval/Comment:

保存したレビューの復元方法を文書化する
Approval/Comment:
```

結果ファイルの `Approval/Comment:` には空欄（未確認）、`Approved`、Go形式で引用・エスケープされた `Comment: "..."` だけを認めます。提案文は空でない単一行とし、不正なUTF-8、置換文字 `�`、制御文字、同一提案内の同じ文言の重複は拒否します。生成結果・保存時・既存提案の読み取りと履歴検証でも重複を拒否し、既存ファイルを自動修正しません。改訂で同じ項目を引き継ぐ場合など、別世代に同じ文言が残ることはあります。`parent.txt` は直前の `review.*` ディレクトリ名を保持します。新しい改訂は内容が厳密に `restructure\n` の `revision.txt` も持ち、親との位置対応を必要としない総合的な再構成を示します。どちらのマーカーもない旧改訂には従来の位置ベースの検証を適用します。つまり、親の未承認項目ごとに同じ順序で1項目を置き、未確認項目の文言は変えません。内容が厳密に `followup\n` の `followup.txt` は、位置による置換ではなく独立した追加確認事項を示します。`revision.txt` と `followup.txt` は排他的で、ルート提案にはどちらも置けません。履歴構造の検証は、過去の承認との意味的な整合性を機械的に証明するものではありません。リンクのない旧改訂を同じ系列と推測することはありません。

`generate` と `revise` は固有の `review.*` ディレクトリを作成し、必要ならローカルGitの `info/exclude` に `/prop-review-tmp/` を追加します。レビューだけではGit設定を変更しません。依頼文やコメントがローカルに保存されるため、内容に注意してください。

## エンジンと失敗時の動作

提案生成コマンドでは、エンジンにリポジトリの参照と提案の作成だけを指示し、実装は指示しません。`flow` は例外で、前述のとおりツールを使って承認済み作業を実行します。以下の応答検証と制限は提案生成についての説明です。応答は1～10件の単一行の提案を含むJSON配列として検証し、追加確認の検査では空配列も受け付けますが、コメントによる再構成では1～10件を必須とします。言語は自動検証しません。処理内容に応じたスピナーを標準エラー出力に表示し、100秒でタイムアウトします。エンジンのプロセスの標準出力は16 MiB、標準エラー出力は64 KiB、`npm root -g` の標準出力は8 KiBに制限します。超過時は収集中にプロセスを停止し、明示的なエラーを返します。不正な応答・失敗・入力中断時に以前のファイルは上書きしません。

Piでの生成は、拡張・スキル・プロンプトテンプレートを無効にした読取専用SDKセッションを使います。fxでの生成は `fx ask --no-save --json` を使い、`final_output` のみを採用し、蓄積された出力は使いません。指示だけではfxのツール権限を強制できません。fxのローカル設定・フック・プラグインによる副作用には注意してください。

完了したレビュー結果をチャットに取り込み、コメントへの回答を得るには `prop-review-ingest` スキルを使います。`prop-review` スキルは提案生成とレビューへの引き渡しを扱います。承認はその項目だけへの判断であり、実装は自動開始しません。
